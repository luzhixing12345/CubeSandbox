Cube XFS + JFS 分层存储方案

nbdkit 提供统一块设备视图，XFS 承担运行时热路径，JFS 保存共享、可恢复的远端 generation

前端、数据面与后端

Cube 只接触临时 NBD 设备；卷身份由 volume ID、generation 和 manifest 决定，不把 /dev/nbdX 写入持久元数据。

VMM 前端 NBD 接口 nbdkit 数据面 本地 XFS 共享 JFS

前端：Cube / Hypervisor

  • Cubelet 调用 cubestor 管理 export、NBD 设备和 generation。
  • rootfs 作为 virtio-blk 后端；memory 作为 MAP_PRIVATE backing。
  • CubeMaster 管理调度、LOCAL_READY / REMOTE_READY 和跨机门禁。

后端：local overlay + shared baseline

  • XFS local 保存 clean read cache 和尚未发布的 dirty overlay。
  • JFS shared 保存不可变 baseline、manifest 和远端已提交 generation。
  • nbdkit 按 4 KiB 页查 local map，miss 回源 JFS 并回填 XFS。

运行时数据路径

memory 和 rootfs 的读路径相同，但运行期写语义不同。切换标签查看。

页状态

  • ABSENT：本地没有，读取 shared。
  • ZERO：逻辑零页，不访问 shared。
  • FROM_SHARED：从 JFS 回填的 clean cache。
  • LOCAL：客户端修改的 dirty 数据，发布前不可淘汰。

缓存层次

NBD page cache、nbdkit 本地文件 page cache 和 JuiceFS cache 可能同时存在。上线前要用实际 workload 评估重复缓存、readahead 和内存压力。

generation 状态机

API 返回和跨节点恢复必须使用不同的提交点。READY 状态只允许单向推进。

CREATING创建 local/shared pair
→
ACTIVE_LOCAL持有 writer lease
→
SEALED_LOCAL本机可恢复
→
PUBLISHING后台上传与校验
→
READY_REMOTE允许跨节点恢复
关键规则：clean cache 可以删除；未发布 dirty overlay 是唯一数据副本，必须 pin。节点故障零丢失只有在 REMOTE_READY 后才能保证。

一致性边界

动作必须保证完成后的能力
NBD WRITE写入 local page cache；按约定可尚未落盘当前进程继续运行
FLUSH / FUAdata → map → header 按序持久化，目录元数据可恢复节点重启后恢复 local generation
LOCAL_READYrootfs、memory、VM state、manifest 均 sealed源节点恢复；API 可以返回
REMOTE_READY远端对象校验完成并发布 commit marker跨节点恢复
GC无 active lease、mmap pin、上传任务和后代引用删除 local cache 或 remote generation

现有原型必须补齐

  • 新增 raw rootfs/memory → NBDOVL01 的 import。
  • 已有块原地覆盖改为 COW 或 WAL。
  • sync 从重建整个 shared 文件改为 immutable generation 发布。
  • clone 源增加 freeze/lease，map/data 增加校验。

memory 上线门槛

  • 验证 /dev/nbdX + MAP_PRIVATE 缺页和 readahead。
  • 验证 nbdkit 重启、NBD timeout、断链后的 EIO/SIGBUS。
  • 验证大内存 flat map 占用和 page-fault p99/p999。

设计原则：远端 generation 不可变；本地 clean cache 可丢；dirty overlay 在远端提交前不可丢；NBD 设备号不是持久身份。
